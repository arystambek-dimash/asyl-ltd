# Работа с cv_service

Контекст для агента, который правит этот сервис. Общее описание API и
установки — в `README.md`; здесь только то, на чём легко ошибиться.

## Главное: этот код НЕ доезжает до цеха через CI/CD

`cv_service` живёт на Windows-ПК цеха **отдельной копией**. Пуш в `main` его не
обновляет — CI прогоняет только тесты (`pytest -q cv_service/tests`), а на
машину код попадает вручную:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\install-ai-service.ps1 `
  -ApiKeySha256 '<64-символьный SHA-256>' -ModelPath 'C:\Temp\best.pt' `
  -BackendTailnetIp '<TAILSCALE-IP>' -ModelDevice '0' `
  -PrewarmCameras 'cam2' -MaxActiveProcessors 2
```

Установщик идемпотентен: повторный запуск = обновление. Подробности и порядок
в `deploy/camera-pc/README.md`.

**Практическое следствие.** Новое поле в ответе API появится в CRM только после
ручного обновления цеха. Пока его нет, CRM получает старый ответ и обязана
работать без нового поля. Так уже случилось с `detections`: поле добавили,
задеплоили веб — а рамки на мониторе не появились, потому что ПК цеха отвечал
старой версией. Проверить версию: если в объекте процессора `/always-on` нет
ожидаемого ключа — сервис старый.

Отсюда правило: **любое новое поле ответа должно быть необязательным** на
стороне CRM. Не менять смысл существующих полей и не удалять их — на другом
конце может быть версия на несколько недель старше.

## Что нельзя ломать

**Счётчик мешков — это деньги.** `total`, `per_color` и `confidence_sums`
питают учёт отгрузки в CRM. Любая правка `apply_inference` / `LineTracker`
меняет цифры, за которые платят. Меняя их, нужен тест на конкретный сценарий,
а не только «код запускается».

**Горячий путь кадра.** Цикл чтения → `submit` → `publisher.write` рассчитан на
ПК цеха, а не на dev-машину. Тяжёлая работа в нём просаживает FPS и вместе с
ним счёт. Всё, что нужно наружу, добавляйте в `status()` — он вызывается
опросом и на кадры не влияет.

**Один worker на все камеры.** Inference идёт последовательно через общую
модель; параллелить его нельзя без пересмотра `DroppingFrameQueue` и лимита
`max_active_processors` (по умолчанию 2).

**Проверка поколения источника.** В `apply_inference` есть сравнение
`source_generation` — кадр от прошлого источника (sub/main) не должен попасть
в трекер нового. Это защита от подмены счёта при переключении качества.

## Устройство в двух словах

- `app.py` — FastAPI, все ручки под `X-Api-Key`, CORS и docs выключены.
- `processor.py` — `CameraProcessor` (кадры, статус) и `LineTracker` (счёт
  пересечений линии), `ProcessorManager` (общая модель и очередь).
- `runtime.py` — обёртка модели, отдаёт `Detection` в пикселях кадра; там же
  `validate_classes`.
- `contracts.py` — `Detection(x1, y1, x2, y2, confidence, label)`.
- `settings.py` — всё из env: `AI_INFERENCE_FPS` (8), `AI_OUTPUT_FPS` (12),
  `AI_MAX_ACTIVE_PROCESSORS` (2), `AI_MODEL_DEVICE` (`0`).
- `conveyor.py` — отдельный Modbus/TCP I/O-thread. Inference только обновляет
  cached total/heartbeat; сетевой I/O в `apply_inference` запрещён. Любой fault,
  stale AI, target или shutdown имеет приоритет `OFF` и защёлкивает сессию.
- `cloud_conveyor.py` — observation-only HTTPS worker для server-managed ESP.
  Inference только coalesce-ит последнее состояние; HTTP выполняется отдельным
  потоком. Этот режим не пишет локальный выход и не имеет readback.

Метка класса — `Цвет_Вес`, например `Red_50`: `validate_classes` требует
`.+_[1-9][0-9]*` и роняет запуск на чекпоинте с другими классами. CRM
разбирает цвет по части до `_`. Wagon detector — отдельный adapter; общую
модель мешков нельзя использовать как его fallback.

## Два режима

- **`session`** — отгрузка. Публикуется поток `cam<N>ai` с вжатыми рамками
  (`_annotate`), идёт запись.
- **`always_on`** — фон 24/7. `publishing = self.mode == "session"`, поэтому
  аннотированный поток **не публикуется**. Рамки для этого режима отдаются
  координатами в `status()["detections"]` — CRM рисует их поверх обычного
  потока сама.

`detections` — доли кадра (0..1), не пиксели: разрешение меняется при
переключении sub/main, а вёрстка в браузере от него зависеть не должна.
Флаг `counted` помечает рамку, которую принял счётчик.

## Тесты

```bash
pytest -q cv_service/tests
```

Юнит-тесты собирают `CameraProcessor` через `__new__` и подставляют поля
вручную (см. `_overlay_processor` в `tests/test_service.py`). Добавили поле в
`__init__` — добавьте и в фикстуры, иначе тесты упадут на `AttributeError`.
`per_color` и `confidence_sums` в фикстурах должны быть `defaultdict`, иначе
подсчёт падает на `KeyError`.

Отдельный джоб CI (`Camera AI service contract`) гоняет эти тесты на каждый
пуш — они единственная защита от регрессии счёта, пока цех не обновлён.
