# AI-сервис камер

Windows-служба читает нормализованный RTSP-поток MediaMTX, выполняет детекцию
одной общей моделью `best.pt` и считает пересечения линии. H.264 поток
`cam<N>ai` публикуется только во время отгрузочной сессии; фоновый режим 24/7
работает без публикации и записи. На каждый активный `cam<N>` существует один
decoder, а inference всех камер проходит через единственный последовательный
worker общей модели.

> **Лицензия модели:** production-установка не меняет лицензионные права.
> До развёртывания нужно подтвердить, что проект выполняет AGPL-3.0 либо у
> организации есть подходящая коммерческая лицензия Ultralytics для закрытого
> внутреннего/edge-развёртывания.

## API

Все запросы требуют `X-Api-Key`. Query-параметр с ключом не поддерживается,
CORS и интерактивная документация отключены.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | модель, MediaMTX, processors и последние кадры |
| GET | `/events?after_id=0&limit=500&cam=cam3` | журнал пересечений после серверного cursor |
| GET | `/cameras` | инвентарь MediaMTX и AI-состояния |
| GET | `/cameras/cam2/line` | сохранённая линия подсчёта камеры |
| PUT | `/cameras/cam2/line` | атомарно сохранить и применить линию |
| GET | `/processors` | тёплые processors |
| GET | `/always-on` | выбранные фоновые processors и их состояние |
| PUT | `/always-on` | атомарно заменить постоянный список камер |
| GET | `/camera-roles/wagon-number` | назначенная камера номера вагона |
| PUT | `/camera-roles/wagon-number` | закрепить одну камеру за Wagon OCR 24/7 |
| POST | `/wagon-number/detect` | найти табличку на JPEG-кадре |
| DELETE | `/recordings` | удалить перечисленные сегменты записи с ПК камер |
| GET | `/processors/cam2` | состояние одной камеры |
| POST | `/processors/cam2/prewarm` | прогреть decoder/inference в `IDLE` без записи |
| POST | `/processors/cam2` | обнулить и перейти в `COUNTING` |
| POST | `/processors/cam2/session` | подготовить привязанную к заказу цель при подтверждённом `OFF` |
| POST | `/processors/cam2/conveyor/start` | включить привязанный конвейер и проверить read-back |
| POST | `/processors/cam2/conveyor/stop` | защёлкнуть `OFF`, не закрывая подсчёт |
| POST | `/processors/cam2/conveyor/emergency-stop` | физически записать/проверить `OFF` без живого AI-процессора |
| POST | `/processors/cam2/reset` | обнулить текущий подсчёт |
| DELETE | `/processors/cam2` | заморозить результат и вернуться в `IDLE` |

`POST` принимает только безопасные настройки, никогда URL:

```json
{"source":"sub","line":"0,0.5,1,0.5","direction":"any"}
```

Camera ID строго соответствует `cam<N>`. Новый `POST` к уже считающему
processor идемпотентен и не сбрасывает результат. После `DELETE` обычная камера
остаётся прогретой в `IDLE`, а выбранная камера сразу возвращается в 24/7;
FFmpeg publisher в обоих случаях закрывается.

## Конвейер ESP32: прямой Modbus

Контроллеры задаются только на camera-PC через
`AI_CONVEYOR_CONTROLLERS_JSON`; HTTP-клиент не может передать IP, unit ID или
адрес регистра. Поддерживаются Modbus/TCP coil и holding register. Отдельный
`feedback_address` обязателен и не может совпадать с командным регистром в том
же register space: echo команды не доказывает положение контактора. Адреса в
конфигурации нулевые, без привычного префикса `4xxxx`. Все command/feedback
точки должны быть раздельными и уникальными между камерами; сервис отклоняет
конфигурацию с любым пересечением.

Пример для команды в holding-регистре `0` и feedback в регистре `1`:

```json
{"cam2":{"host":"192.0.2.10","port":502,"unit_id":1,"register_type":"holding","address":0,"on_value":1,"off_value":0,"feedback_register_type":"holding","feedback_address":1,"feedback_on_value":1,"feedback_off_value":0}}
```

Запуск двухфазный: `/session` обнуляет новый счётчик, фиксирует неизменяемые
`session_id`/`target_total`, отправляет `OFF`, проверяет read-back и ждёт первый
inference этой сессии. Только после commit заказа backend вызывает
`/conveyor/start`. Достижение `total >= target_total`, ручной стоп, устаревший
AI или ошибка Modbus защёлкивают терминальный `OFF`; запоздалый `ON` уже не
возобновляет движение. Счёт после стопа продолжается, чтобы сохранить выбег и
видеть превышение цели. Edge постоянно переотправляет и перечитывает не только
`ON`, но и `OFF`: закэшированный успешный ответ не считается продолжающимся
доказательством остановки.

При каждой новой сессии RTSP decoder открывается заново, а старые/буферизованные
кадры отбрасываются по generation fence. Первый кадр служит только baseline:
только изменившееся содержимое центральной области доказывает движение
видеопотока и может обновить AI heartbeat. Повторяющийся frozen-кадр его не
обновляет. Во время `ON` отсутствие прироста счётчика 15 секунд
(`AI_CONVEYOR_NO_PROGRESS_SECONDS`, максимум 30) и абсолютные 300 секунд работы
(`AI_CONVEYOR_MAX_RUN_SECONDS`, максимум 900) также терминально выключают
привод. Полностью статичная исправная сцена может дать безопасный ложный стоп;
для устранения этого ограничения нужен физический encoder/photoeye от линии.

Аварийный `POST /processors/{camera}/conveyor/emergency-stop` выполняет свежую
запись/проверку `OFF` даже после потери in-memory AI-процессора. Он также
блокирует повторный запуск того же `session_id`; новый заказ получает новый ID.

Modbus/TCP сам по себе не является контуром функциональной безопасности.
В нём нет аутентификации или TLS, поэтому TCP/502 ESP32 должен быть закрыт
ESP-side firewall/allowlist только для IP camera-PC и находиться в отдельном
VLAN; доступ прочих рабочих станций/PLC запрещён. Без этого условия удалённый
smart-режим вводить в эксплуатацию нельзя.
Прошивка ESP32 обязана при загрузке держать выход `OFF` и снимать его, если
запись-heartbeat не пришла не позднее чем через 2 секунды; после восстановления
связи автозапуск запрещён. Обычный Modbus-регистр не доказывает наличие этого
watchdog: пока прошивка и физический kill/network-loss тест не подтверждены,
smart-режим вводить в эксплуатацию запрещено. Для следующей версии прошивки
рекомендуется отдельный version/capability-регистр `watchdog_enabled`, но он не
заменяет испытание. E-stop, защита двигателя, концевики и контактор должны
работать независимо от Python/ESP32. Для настоящего подтверждения остановки
feedback берётся с отдельного вспомогательного контакта контактора, а не из
командного регистра.

### Cloud ESP: только исходящие AI-наблюдения

Альтернативный режим задаётся `AI_CONVEYOR_CLOUD_CAMERAS=cam2,...`, строго
каноническим `AI_CONVEYOR_CLOUD_API_URL=https://asyl-ltd.kz/api/conveyors/v1/ai/observation/`
и отдельным `AI_CONVEYOR_CLOUD_API_KEY`. Одна камера не может одновременно
присутствовать здесь и в `AI_CONVEYOR_CONTROLLERS_JSON`; сервис прекращает
запуск при пересечении. Backend создаёт такую сессию с
`"conveyor_transport":"cloud"`. Значение по умолчанию `direct` сохранено для
совместимости со старыми backend-версиями, но для cloud-камеры оно отклоняется.

Camera-PC в cloud-режиме **не включает выход**, не вызывает локальный Modbus и
не заявляет физический readback. В статусе явно возвращаются
`transport=cloud`, `direct_control=false`, `write_readback=false` и
`feedback=null`. Единственная роль edge — неблокирующе передавать результат
счётчика серверному lease-контроллеру.

Отдельный coalescing-worker отправляет не чаще 2 активных наблюдений в секунду
на камеру; inference только заменяет последнее значение в памяти. Цель и
terminal-события будят worker немедленно. Запрос идёт с проверкой TLS и
`Authorization: Bearer <AI_CONVEYOR_CLOUD_API_KEY>` и содержит ровно:

```json
{"protocol_version":1,"camera":"cam2","session_id":123,"target_total":50,"edge_boot_id":"<UUID>","seq":7,"total":18,"terminal_reason":null}
```

`edge_boot_id` меняется при запуске службы, `seq` монотонно растёт. Не
подтверждённый terminal повторяется с теми же `edge_boot_id`/`seq`/payload,
поэтому сервер может безопасно ответить `duplicate=true`. Исключения HTTP/TLS
не попадают в inference и не логируют ключ; при потере наблюдений серверный
lease обязан сам перейти в `OFF`. Новый session отменяет retry старого.
Outbound-ключ в открытом виде необходим camera-PC для Bearer-запроса и хранится
в защищённом ACL `service-env.json`; backend хранит только его SHA-256.

Перед цеховым запуском физически проверить: power-on `OFF`; остановку при
обрыве сети и убийстве `ai_service.py`; отсутствие автозапуска после reconnect;
изоляцию TCP/502 от любого узла кроме camera-PC; срабатывание E-stop; fault при
заваренном контакторе; фактический выбег мешков
после линии счёта. Если между линией и сбросом уже находятся мешки, для точной
цели нужен верхний затвор/вторая камера либо откалиброванный упреждающий стоп.

## Установка

На camera-PC применяется
[`deploy/camera-pc/install-ai-service.ps1`](../deploy/camera-pc/install-ai-service.ps1).
Он создаёт отдельный venv, копирует checkpoint, выполняет model warm-up,
проверяет MediaMTX и H.264 encoder, защищает файлы ACL, открывает порт 8890
только для Tailscale-IP backend и регистрирует boot-задачу `SYSTEM`.
Рабочее состояние хранится в соседней папке `state`, а не в заменяемом пакете
`cv_service`. В частности, `AI_EVENT_DB_PATH` указывает на сохраняемый
`state/count-events.sqlite3`. При первом обновлении installer переносит известный старый
`cv_service/data/camera-roles.json` до удаления пакета. Если старый и новый
файлы уже существуют и различаются, установка останавливается без
перезаписи — оператор должен сначала сверить их вручную.

Для входящего API на camera-PC сохраняется только
`AI_SERVICE_API_KEY_SHA256`; его plaintext остаётся в production backend.
Исключение — отдельный исходящий `AI_CONVEYOR_CLOUD_API_KEY`, если включён
cloud ESP: он нужен для Bearer-запроса и защищается ACL installer. Получить
digest входящего ключа можно локально:

```powershell
python -c "import hashlib,os; print(hashlib.sha256(os.environ['AI_SERVICE_API_KEY'].encode()).hexdigest())"
```

Ручной запуск для диагностики из корня репозитория:

```powershell
.\.venv\Scripts\python.exe cv_service\ai_service.py
```

До вызова `uvicorn.run` сервис проверяет checkpoint/классы, выполняет warm-up,
выбирает `h264_nvenc`, `h264_qsv` или `libx264` и поднимает настроенные
`AI_PREWARM_CAMERAS`. При любой ошибке HTTP-порт не запускается.

## Постоянный подсчёт без фоновой записи

`PUT /always-on` принимает список `cam<N>` и атомарно сохраняет его в
`AI_ALWAYS_ON_STATE_PATH`. После перезапуска Windows-службы выбранные
процессоры восстанавливаются до открытия HTTP-порта. Они непрерывно читают
камеры и выполняют inference, но не публикуют `cam<N>ai`, поэтому MediaMTX не
создаёт фоновые видеозаписи.

Линии из `PUT /cameras/cam<N>/line` хранятся отдельно в
`AI_COUNTING_LINES_STATE_PATH`. Обновление работающего processor сбрасывает
только его краткоживущие tracks, но не уже накопленный итог. Новый processor
автоматически получает сохранённую линию; `GET /cameras` возвращает те же
настройки в `line_configs` для стены камер.

Каждое фактическое пересечение линии сначала синхронно фиксируется в SQLite
журнале, и только после успешного commit увеличивает live-счётчик. При временной
ошибке записи shared inference fail-closed повторяет тот же `event_key` до
успеха; новые кадры не обходят незаписанный мешок, а `/health` остаётся доступен
и возвращает `degraded`. Неисправимая schema/content ошибка не ретраится.
`GET /events` возвращает глобальные возрастающие `id`, `journal_id`,
`events`, `next_after_id` и `has_more`; `limit` допустим от 1 до 500. Фильтр
`cam` не перенумеровывает глобальные ID, а пустая страница возвращает исходный
`after_id`. Backend хранит cursor вместе с `journal_id`, применяет каждый
`event.id` один раз и прекращает импорт при неожиданной смене identity.

Первый переход с отдельного production build требует ручной миграции: до
переустановки экспортировать `line_configs` из авторизованного `GET /cameras`,
после установки повторить каждый config через `PUT /cameras/cam<N>/line` и
сверить новый `GET /cameras`. Путь старого локального хранилища неизвестен,
поэтому installer намеренно не угадывает и не удаляет его. Обычный deploy
backend не обновляет camera-PC; этот шаг нужен только перед ручным запуском
`install-ai-service.ps1`.

Если отдельный production build уже накопил count events, перед первой
canonical-установкой сервис нужно остановить и перенести его совместимый SQLite
journal с сохранением всех строк и ID (вместе с `-wal`/`-shm`, если они
существуют) в `state/count-events.sqlite3`. Начинать новый пустой journal после
серверной догрузки нельзя: его ID снова пойдут от 1 и пересекутся с аудитом CRM.
Старый путь и схема неизвестны, поэтому installer их не угадывает; если схема
несовместима, обновление откладывается до явной миграции и сверки cursor.
После первого canonical запуска sibling DB не удаляется при повторной
установке; удалять или заменять её вручную нельзя, поскольку это меняет
`journal_id` и разрывает серверный cursor.

При `POST /processors/cam<N>` прогретый процессор переключается в режим
отгрузочной сессии, обнуляет её счётчик и начинает публикацию/запись. `DELETE`
закрывает публикацию и сразу возвращает выбранную камеру в режим 24/7.

## Камера номеров вагонов

`PUT /camera-roles/wagon-number` принимает одну камеру и основной поток:

```json
{"camera":"cam1","source":"main"}
```

Назначение атомарно сохраняется в `AI_CAMERA_ROLES_STATE_PATH` и
восстанавливается после перезапуска Windows-службы. Перед сохранением сервис
проверяет, что поток существует в MediaMTX. Это отдельная роль камеры: она не
запускает модель подсчёта мешков и не занимает её processor. OCR-worker будет
подключён к этому назначению отдельным этапом.

Канонический `POST /wagon-number/detect` принимает только JPEG не больше
`AI_WAGON_FRAME_MAX_BYTES`. Детектор табличек является отдельной capability:
его нельзя подменять общей моделью мешков, иначе любой мешок мог бы открыть
ложный приход. Наблюдаемая production-реализация использует отдельные
`wagon-number.pt` и Paddle OCR, но их runtime и веса в этот репозиторий не
входят. Поэтому текущий канонический build честно отвечает HTTP 503, а
`/health` сообщает `capabilities.wagon_plate.available=false`, пока отдельный
проверенный detector adapter не передан в `ProcessorManager`. Это намеренный
fail-closed режим, а не эквивалент production OCR.

## Финализация

Live snapshot остаётся частью управления сессией, но финансовый поток мешков
восстанавливается из durable `/events`. Backend сначала догружает события и
атомарно обновляет PostgreSQL вместе с cursor, затем фиксирует финальный
snapshot и вызывает `DELETE`. Если DELETE не удался, сессия остаётся открытой
и завершение можно безопасно повторить. Видеофайлы остаются в MediaMTX на
camera-PC и удаляются его 14-дневной retention-политикой.
