## Архитектурные решения

Сохранён модульный Django-монолит и существующий frontend query layer. Публичные URL, HTTP methods и названия полей не менялись. Входы, которые раньше давали 500 или создавали противоречивые данные, теперь отклоняются с 400. Конкурирующая синхронизация датасета получает 409.

Три целевых изменения ответственности:

1. Изменение Task проходит через сервис; serializer перестал напрямую сохранять весь устаревший объект.
2. `grain/queries.py` отделяет проекцию списка от команд учёта. Аннотированные значения не используются как источник истины для складских проводок.
3. Работа с обучающими фото имеет отдельную очередь и взаимное исключение операций. Денежная очередь и денежные блокировки в этом не участвуют.

Advisory lock датасета использует PostgreSQL session semantics, соответствующие текущему прямому подключению Compose. При переходе на PgBouncer transaction pooling эту реализацию нужно заменить согласованным механизмом lease/блокировки. При ошибке транзакции соединение закрывается, чтобы session lock не утёк.

Миграции схемы не требуются. Новые CHECK constraints на существующих данных намеренно не вводились до диагностики допустимых исторических значений.

### Браузерный сценарий с реальным локальным backend и PostgreSQL

Использовались временная БД, тестовые клиент/кассир и заказ на 20 000 ₸. ApiPay и Camera-PC в этом окружении направлены на неработающий локальный адрес; обращения к производственным системам исключены настройками тестового окружения.

1. Вход через UI → JWT API → кабинет клиента.
2. Открытие заказа: 2 мешка × 10 000 ₸, остаток 20 000 ₸.
3. UI «Наличными» → POST portal pay → Payment `requested`, UI «Ожидает подтверждения кассиром».
4. Отдельный авторизованный запрос кассира → receive API → Payment `confirmed`, Order `settled`, paid_total `20000.00`, remaining `0.00`.
5. Тот же открытый браузер без reload показывает «Оплачен» и кнопку квитанции.
6. Offline: видна ошибка обновления и сохранён последний заказ. Online: ошибка исчезает при успешном обновлении. Ошибок JavaScript/Next.js overlay не обнаружено.

Снимки: [выбор оплаты](evidence/portal-payment-before.png), [внешнее подтверждение](evidence/portal-payment-settled.png), [потеря связи](evidence/portal-payment-offline.png).

Это подтверждает UI → API → service → DB → response → повторное чтение → UI. Реальное получение денег ApiPay и работа физического оборудования покрыты локальными контрактными тестами/моками, а не испытанием на оборудовании.

### Дополнение к проверке зависимостей

Поздний запуск pip-audit обнаружил advisories в исходном локальном окружении: Django 5.2.15, DRF 3.17.1, sqlparse 0.5.5, а также pip/setuptools и Starlette. Starlette не объявлен зависимостью этого Django-приложения и отсутствует в разрешённом production-графе. Лишние пакеты общего локального .venv не удалялись. Наличие advisory само по себе не доказывает достижимую уязвимость конкретного endpoint.

Основания обновления: [Django security release](https://www.djangoproject.com/weblog/2026/aug/04/security-releases/), [DRF: ограничения размера request body](https://github.com/advisories/GHSA-2m8g-3cmr-wg3w), [DRF: AdminRenderer](https://github.com/advisories/GHSA-g47c-3xmw-q6m2), [sqlparse ReDoS](https://github.com/andialbrecht/sqlparse/security/advisories/GHSA-prg7-hcfm-mfcr), [PostCSS sourceMappingURL](https://github.com/advisories/GHSA-fxqj-rqcc-2cmp).
