# Номера вагонов: проверка в браузере

Проверено 7 сентября 2026 года в production-сборке Next.js на локальном порту 3018
с настоящими Django API на 8118 и отдельной PostgreSQL БД `asyl_transport_preview`.
Камеры подменены локальными статусами; внешний HTTP отключён. Production-данные,
взвешивания, запуски камер и реальные отгрузки не изменялись.

## Результаты

- **Редактирование номера:** заказ вагона открылся с `00123456`. Ввод другого
  семизначного номера блокирует продолжение с понятным сообщением. После ввода
  `00012345` запрос PATCH вернул 200, модалка закрылась, страница и PostgreSQL
  сохранили полный номер с ведущими нулями.
- **Старый номер:** существующий семизначный `1234567` разрешено оставить без
  изменения. Через форму изменено количество мешков с 40 на 41; PATCH вернул
  200, PostgreSQL подтвердил новое количество и прежний номер.
- **Конкурирующее начало погрузки:** после открытия формы только в тестовой БД
  заказ переведён в `loading`. Попытка сохранить другой номер вернула 400,
  модалка показала запрет изменения после начала погрузки. PostgreSQL сохранил
  исходный `00012345`; затем состояние тестового заказа восстановлено.
- **Отгрузка:** видны полные `Вагон 00012345` и `Вагон 1234567` рядом с прежним
  автомобильным знаком `123 ABC 02`.
- **Портал клиента:** поле называется «Номер вагона»; клиент сохранил `00007777`
  в заказ без чужого владельца номера. PATCH портала вернул 200, текущий номер
  обновился в UI и PostgreSQL.
- **Узкий экран 390 px:** форма валидации, список отгрузки и портал читаемы;
  горизонтального переполнения страницы нет (`scrollWidth = innerWidth = 390`).
  Ошибок Next.js overlay не обнаружено.
