# CI/CD: причины и изменения

## Что показала история GitHub

Последние CI `34015908997` и `34015469240` отменены во время установки зависимостей: тесты ещё не выполнялись. Это не доказательство падения тестов. По данным этих запусков нельзя достоверно установить, кто или что запросило отмену. Для тех же commit запускались отдельные успешные ручные deploy. Автоматический deploy после отменённого CI пропускался.

Последний найденный CI со статусом failure — [32022135731, 17 августа](https://github.com/arystambek-dimash/asyl-ltd/actions/runs/32022135731): `npm ci` отказался работать из-за рассинхронизации lock-файла и отсутствующих `@emnapi/*` зависимостей. Текущий package-lock проверен чистой установкой npm 10.9.8 в отдельном пустом каталоге: успешно установлены 652 пакета.

## Исправления

- Активный CI main не отменяется следующим push; устаревшие проверки PR можно отменять. Для повторного запуска доступен workflow_dispatch. Внешнюю или ручную отмену эта настройка предотвратить не может.
- Ключ pip cache учитывает и `requirements.txt`, и вложенный `requirements-prod.txt`.
- Тестовый runtime использует быстрый password hasher; production-настройки не изменены, модуль запрещает запуск вне тестов. Это сокращает стоимость массового создания пользователей.
- `npm ci` не повторяет аудит, который уже выполняется отдельным шагом. Добавлен кэш `.next/cache` с разделением по ОС, версии Node и lock-файлу.
- Результаты pytest сохраняются как JUnit artifact. Ошибка информативного Python audit больше не превращается в success через `|| true`; шаг выдаёт видимый warning. Аудируется production dependency graph.
- Перед сборкой release проверяется последний CI этого SHA, main и этого репозитория. PR, другой SHA, отмена, failure и незавершённый CI не подходят. Старый успешный запуск не маскирует новый неудачный.
- Docker-образы backend/frontend собираются отдельными параллельными jobs. Deploy и recovery получают оба digest через явные needs. Health gates, блокировки выпуска и rollback сохранены.
- README приведён в соответствие с фактическим camera health gate: он проверяется при выпуске, включая готовность журнала событий.

Правила concurrency и поля ответа сверены с [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) и [REST API workflow runs](https://docs.github.com/en/rest/actions/workflow-runs).

## Проверки до push

- 2142 backend-теста + 3 subtests прошли за 270 секунд; после небольшого дополнения CORS — 68 связанных проверок, после уточнения сообщений взвешивания — 19 тестов вывоза.
- 524 frontend-теста; форматирование, lint, typecheck и production build прошли.
- 37 тестов deploy/backup/recovery и проверки допуска release прошли.
- actionlint 1.7.12: ошибок workflow нет. Проверка shellcheck при этом отключена; существующие shell-сценарии проверены deploy-тестами.
- Чистый npm ci успешен. Django system check и makemigrations --check не нашли проблем.

Это результаты локальной проверки. Результаты GitHub CI и выпуска после push сообщаются отдельно. Воспроизводимый Python lock с полным набором hashes остаётся задачей A20 исходного аудита.
