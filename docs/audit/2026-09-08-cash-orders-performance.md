# Касса и заказы: оптимизация загрузки

Исходная версия: `f5c15db`. Изменения не затрагивают запись оплат,
взвешивание или отдельную разработку автоматики конвейеров.

## Найденные причины

- «Общее» кассы загружало полные оплаты одновременно со скрытой вкладкой
  подтверждения и её списком заказов. Скрытая очередь продолжала опрашиваться.
- Для поиска и любой нестандартной сортировки заказов фронтенд отключал
  пагинацию и скачивал всю историю. Сортировка активных/выехавших заказов
  применялась в браузере, поэтому при пагинации не была глобальной.
- Сводка отделов и список долгов создавали Python-объекты всех исторических
  позиций и оплат, хотя им нужны только суммы.
- Вложенные сериализаторы истории оплат создавались заново для каждого заказа.
- Счётчики четырёх статусов транзакций делали четыре отдельных COUNT-запроса.
- Форма заказа, раздел транзакций и справочник редактирования отделов
  загружались до использования соответствующих действий.

Основные тесты N+1 проходили и в исходной версии. Причинами оказались лишние
запросы, загрузка полных наборов данных и повторная обработка объектов;
подтверждённого SQL-запроса на каждую строку в проверенных списках не найдено.

## Изменения

- Поиск и сортировка выполняются до пагинации на сервере; фронтенд всегда
  запрашивает страницы по 50 заказов. Поиск задержан на 300 мс при наборе.
  Поддержаны номер, полное имя клиента, ID и номер машины с пробелами.
- Очереди подтверждения заказов/оплат загружаются только на своей вкладке,
  тоже страницами. Общие итоги оплат получаются через `summary=1`.
  Счётчик вкладки показывается после получения её данных, без ложного нуля.
  После ручного раскрытия нескольких страниц автообновление приостанавливается,
  чтобы не сбросить читаемые строки; ручное обновление и действия доступны.
- Опциональная пагинация очереди сохраняет старый плоский API без `page`.
- Сводки получают суммы через независимые подзапросы позиций и платежей.
  Это не умножает позиции на оплаты при JOIN. Учитываются только подтверждённые
  платежи за вычетом выполненных возвратов; неопределённая цена равна нулю.
  Запись финансовых данных и исходные свойства модели не менялись.
- Сериализаторы вложенных оплат переиспользуются в пределах одного ответа.
  Четыре счётчика транзакций объединены в одну SQL-агрегацию.
- Форма заказа и раздел транзакций выделены в отложенные JS-модули.
  Справочник редактирования отделов загружается при открытии окна.
- «Показать ещё» доступно также в мобильном списке заказов. Показатели,
  рассчитанные по уже загруженным строкам, явно подписаны; сводки отделов
  по-прежнему охватывают весь выбранный период.

## Локальные замеры

PostgreSQL, 300 клиентов/заказов, по две позиции и две оплаты на заказ.
Число SQL включает авторизацию свежего пользователя. Приведены отдельные
замеры локального тестового окружения, не гарантия времени в production.
Сравнение первого холодного запроса списка заказов намеренно не приводится.

| Запрос / данные для страницы | SQL до → после | Время до → после |
| --- | --- | --- |
| Сводка отделов | 6 → 4 | 24,6 → 6,8 мс |
| Долги клиентов | 7 → 5 | 68,4 → 23,7 мс |
| Очередь для обзора кассы: полный список → итоги | 7 → 3 | 65,7 → 3,4 мс |

Размер ответа очереди для обзора: **216 081 → 67 байт** для этого набора
(одна валюта и способ оплаты). Полные строки остаются доступны на вкладке
подтверждения через пагинацию.

Сборки Next.js до/после: First Load JS кассы **268 → 262 КБ**, заказов
**283 → 277 КБ**. Основной выигрыш даёт объём API-ответов, а не JS.

## Проверка

- 711 тестов orders/clients/portal; 571 тест фронтенда.
- Проверки типов, ESLint, Prettier и production-сборка фронтенда.
- `makemigrations --check --dry-run`: изменений схемы нет.
- Тесты числа запросов сравнивают 2 и 20 разных клиентов/заказов, ниже размера
  страницы, поэтому пагинация не маскирует N+1.
- Проверены расчёты с возвратами, неопределёнными ценами, несколько позиций
  и оплат, фильтры, область доступа по отделу, отсутствие пересечений страниц,
  серверный поиск/сортировка и отсутствие загрузки скрытой очереди.

Повтор замеров: из `backend` выполнить
`python -m pytest apps/orders/tests/test_page_performance.py -q -s --reuse-db`.
Значения времени зависят от прогрева и нагрузки машины; границы тестов
закрепляют правильность и число запросов, а не нестабильные миллисекунды.
