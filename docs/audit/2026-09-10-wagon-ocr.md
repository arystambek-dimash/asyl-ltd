# Shipping wagon OCR investigation — 10 September 2026

Four wagon loading segments from cam2/cam12 required operator intervention or
remained unidentified. The saved originals were present, 2560 × 1440 JPEGs.
Each segment had one recognition attempt and an OpenAI response ID. Segment 4
retained `number_unreadable`; operators had already corrected segments 1–3,
which clears their current error. Original upstream text is not recoverable
from the response ID because requests use `store: false`.

## Evidence and reproduction

Read-only probes used the stored originals, never a new live camera frame.
No expected identifiers, order candidates or operator corrections were supplied
to the model. Candidate numbers were checked only after the response.

| Segment | Start, Almaty | Reference | Reference source |
| --- | --- | --- | --- |
| 1 | 09:14 | 28349322 | Explicit operator confirmation |
| 2 | 11:11 | 28816015 | Operator-entered session |
| 3 | 12:07 | 28039261 | Operator-entered session |
| 4 | 14:34 | 28039006 | Original-frame visual reading; not an operator correction |

The previous `gpt-5-mini/high` path failed all three replayed frames 2–4:
wrong digits/checksum or abstention. Cropping the number band did not fix it.
`gpt-5.4-mini/original`, `gpt-5.4/original`, `gpt-5.6-luna/original` and
`gpt-5.6-terra/original` also failed the tested stencil numbers. A successful
HTTP response therefore did not imply a usable transport identity.

`gpt-6-astra/original`, medium reasoning, a 3000-token output ceiling and an
instruction explaining normal stencil bridges correctly read segments 1, 3
and 4. The same outcomes were reproduced using a crop from each original.
Segment 2 was read as 23816015 rather than 28816015 and correctly rejected by
the existing checksum check. This is an improvement on these examples, not a
claim of universal accuracy or a passed full automation acceptance test.

## Release behavior

- Wagon-only `SHIPPING_WAGON_AI_MODEL` and `SHIPPING_WAGON_AI_DETAIL` settings
  travel through Django, Compose and the production deploy's atomic `.env` sync.
  Empty model inherits `WEIGHING_AI_MODEL`; empty detail defaults to `high`.
  Repository variables explicitly select the evaluated production combination.
- Wagons retain one OpenAI request on the stored start frame, with stencil
  guidance and medium reasoning. No continuous number rereading, semantic retry
  loop, fresh photo substitution or checksum-based digit repair is added.
- Truck OCR remains the native model followed by the existing inexpensive GPT
  fallback with `high` detail and low reasoning. The weighbridge is unchanged.
- Original photos, bag events, manual identities and segment boundaries remain
  intact. Technical retries continue to use the same saved evidence and lease
  fences. Ambiguous identifiers still require an operator.

At the observed full-frame usage, the evaluated wagon request costs roughly
US$0.06–0.07 at current standard/cache-write rates. There is one request at the
start of a segment, not one per bag. See the official
[model pricing](https://developers.openai.com/api/docs/models/gpt-6-astra) and
[image detail guidance](https://developers.openai.com/api/docs/guides/images-vision).

The unresolved stencil ambiguity in segment 2 requires clearer visual evidence
or a recognition approach validated on additional labelled frames. Do not make
the displayed success rate look better by accepting an invalid checksum,
injecting the expected identifier into a prompt, or relabelling a manual edit
as an automatic result.
