# POS в кассе: оплата долга по Kaspi QR с телефона

Статус: согласован в чате · 2026-09-12

## Задача

Кассир на телефоне принимает оплату долга как в Kaspi POS: находит клиента,
выбирает заказ в долге, набирает сумму на цифровой клавиатуре — на экране
появляется Kaspi QR (ApiPay `POST /invoices/qr`); клиент сканирует и платит,
экран сам переходит в «Оплачено». Внизу POS — табы «Оплата · Удаленно ·
История», как у Kaspi POS.

Референс: Kaspi Pay → POS (крупная сумма, клавиатура 0–9 и ⌫, «Принять
оплату»; табы Оплата / Удаленно / История / Возврат).

## Решения пользователя

- Вход: крупная круглая кнопка «POS» внизу по центру на всех мобильных
  экранах кассы (как QR-таб Kaspi).
- Табы POS: «Оплата» (QR) · «Удаленно» (счёт на телефон клиента) ·
  «История» (транзакции). Отдельного таба «Возврат» нет — возврат делается
  из строки «Истории», как сейчас.
- Клавиатура принимает только QR; наличные остаются в обычной форме
  «Внести оплату» на странице долга.
- Один заказ за одну оплату; несколько заказов — по очереди.

## Границы

В скоупе: мобильная касса (< 768px), один новый канал на существующем
кассовом эндпоинте оплаты, один новый GET статуса оплаты. Десктоп не
меняется (на десктопе `?view=pos` сводится к «Общему»).

Вне скоупа: оплата нескольких заказов одним QR, наличные/смешанная оплата
в POS, отдельный таб возврата, печать чека, обучалка (следующая задача).

## Бэкенд

### Кассовый Kaspi QR через ApiPay

`POST /api/orders/{id}/payments/` (право `payments.create`), одиночный путь:

- Тело `{"method": "kaspi", "channel": "qr", "amount": "<целые тенге>"}` —
  новый случай. Без `channel` `kaspi` остаётся отметкой о собственном
  POS-терминале кассы (оплата сразу подтверждается, провайдер не
  вызывается) — существующие тесты это фиксируют и не меняются.
- Проверки до создания оплаты: валюта заказа `KZT` (иначе 400
  `apipay_kzt_only`, «QR доступен только в тенге.»); сумма — целые тенге
  (иначе 400 `qr_whole_tenge`, «Kaspi QR принимает только целые тенге.»).
- Оплата создаётся кассовым `add_payment(order, amount, user,
  method="kaspi", stage="requested")` — он проверяет, что оплата открыта
  (заказ отгружен, окно оплаты магазина открыто) и сумма не больше
  доступного остатка с учётом резервов. **Портальный
  `create_client_payment` не использовать**: он переводит заказ в
  «моментальную оплату» (`settlement_intent = "instant"`), и долг пропал
  бы из списка долгов.
- Затем `create_invoice(payment, channel="qr", user=request.user)`.
  Ошибка провайдера (`ApiPayAPIError`, `ApiPayConfigurationError`,
  `ValidationError`) → `_reject_created_payments([payment], user)` и
  ответ `_provider_error(exc)` — как у одиночного онлайн-счёта.
- Ответ 201 — `PaymentSerializer(payment)` после `refresh_from_db()`:
  `status: "requested"`, `provider.channel: "qr"`, `provider.qr_image_url`,
  `provider.qr_token_url`, `provider.qr_expires_at`, `provider.status`.
- Подтверждение денег — существующая механика: вебхук
  `invoice.status_changed` (`paid`) → `apply_invoice_status` → оплата
  `confirmed`; резерв — фоновая сверка ApiPay каждые ~30 с (celery beat).
  Истёкший/отменённый/ошибочный QR (`expired|cancelled|error`) закрывает
  резерв оплаты. Отменить QR у ApiPay нельзя (`qr_cancel_unsupported`).

### Статус одной оплаты

`GET /api/orders/{id}/payments/{pid}/` — `PaymentSerializer` оплаты этого
заказа (404, если оплата принадлежит другому заказу). Права: любое из
`payments.create`, `payments.view`. Скоуп заказа — как у остальных
действий ViewSet (`get_object`). Используется POS для опроса статуса раз
в 3 с.

## Фронтенд

### Экран и вход

- Новый `CashView` = `"pos"` (только телефон; на десктопе → `overview`),
  доступ — `payments.create`. В мобильное меню не входит.
- Круглая кнопка «POS» (иконка QR + подпись) фиксирована внизу по центру
  на всех мобильных экранах кассы, кроме самого POS; только при праве
  `payments.create`. Под контентом — отступ, чтобы кнопка не закрывала
  последнюю строку. Тап → `?view=pos`.
- POS рисует свой `AppShell`: заголовок «POS», раздел «Касса», кнопка «‹»
  в топбаре — шаг назад внутри POS, на первом шаге — закрыть POS (как
  «назад» остальных подэкранов).
- Нижний таб-бар POS: «Оплата» (иконка QR), «Удаленно» (Send), «История»
  (History; только при `payments.view`). Табы — внутреннее состояние POS.

### Поток «Оплата» (QR)

1. **Клиент.** Поиск (автофокус) по списку должников (`/clients/debts/`,
   тот же, что у главной; грузится и для `view=pos`), строки: имя,
   телефон, долг (`CurrencyAmounts`). Локальный поиск по имени/телефону.
2. **Заказ.** `/clients/{id}/debt-detail/` → заказы в долге: `#id · отдел`,
   остаток, «доступно к оплате» = остаток − уже ожидает подтверждения.
   Недоступны (серые, с причиной): не KZT («QR только в тенге»), окно
   оплаты магазина закрыто («Оплата для магазина «…» сегодня недоступна»),
   доступно 0 («Всё уже ожидает подтверждения»).
3. **Сумма.** Крупная сумма, клавиатура 1–9, 0, ⌫; чип «Весь остаток»;
   по умолчанию подставлен весь доступный остаток в целых тенге
   (`floor`); ввод не больше него; кнопка «Показать QR · N ₸» неактивна
   при 0. Если у остатка есть тиыны, подпись «Тиыны (0,50 ₸) — другим
   способом».
4. **QR.** `POST … {method: "kaspi", channel: "qr", amount}` → изображение
   `qr_image_url` (фолбэк без картинки — как в `PaymentQrPreview`), сумма,
   клиент и заказ, «Открыть Kaspi» (`qr_token_url`), «действует до …»,
   «Ожидаем оплату…». Опрос `GET /orders/{id}/payments/{pid}/` каждые 3 с
   (`useVisiblePolling`):
   - `status === "confirmed"` → экран «Оплачено ✓» (сумма, клиент, заказ),
     кнопка «Новая оплата»; список должников перезагружается.
   - `status === "rejected"` или `provider.status ∈ {expired, cancelled,
     error, superseded}` → «QR больше не действует», кнопка «Создать новый
     QR» (к шагу суммы) и «Новая оплата».
   - Предупреждение под QR: «Не создавайте второй QR на эту сумму — старый
     ещё можно оплатить».
   Ошибка создания → текст ошибки на шаге суммы, сумма сохраняется.

### Поток «Удаленно»

Шаги 1–3 те же (выбор сохраняется при переключении табов до выдачи), затем
поле телефона (подставлен `client.phone`, `inputMode="tel"`) и кнопка
«Отправить счёт · N ₸» → `POST … {method: "invoice", amount,
phone_number}` (существующий онлайн-счёт ApiPay). Дальше экран ожидания с
тем же опросом: «Счёт отправлен на +7 …» → «Оплачено ✓» или «Счёт
отменён/истёк». Кнопка «Готово» закрывает ожидание (счёт остаётся в
очереди как «Ожидает клиента»).

### «История»

Существующий мобильный экран транзакций (`TransactionsScreen`) внутри POS
без изменений.

### Общие модули

- `lib/debt-orders.ts`: типы `DebtStore`, `ClientDebtDetail` и функции
  `remainingOf`, `pendingSum`, `moneyCents`, `availableCents`,
  `blockingStore` — переезжают со страницы долга (она импортирует их
  отсюда), POS использует те же правила.
- `components/ui/numpad.tsx`: клавиатура 3×4 (1–9, пусто, 0, ⌫), кнопки
  с доступными именами («Цифра 5», «Стереть»), крупный шрифт, токены темы.
- `components/transactions/qr-code-image.tsx`: изображение QR с фолбэком,
  вынесенное из `PaymentQrPreview` (модалка использует его же).
- `components/cashier/mobile/pos/`: `use-pos-flow.ts` (редьюсер шагов +
  запросы + опрос), `pos-screen.tsx` (AppShell, таб-бар, маршрутизация
  шагов), `pos-steps.tsx` (клиент, заказ, сумма), `pos-result.tsx`
  (QR/ожидание/успех/ошибка), `pos-fab.tsx`.

## Тесты

Бэкенд (`apps/orders/tests/test_staff_pos_qr.py`, ApiPay замокан через
`apps.orders.apipay.urllib.request.urlopen`):
1. `kaspi` + `channel=qr` → 201, ApiPay вызван на `/invoices/qr` с суммой,
   оплата `requested`, провайдер `qr` с картинкой, у заказа
   `settlement_intent` остался `debt`.
2. Заказ в USD → 400 `apipay_kzt_only`, оплат нет, ApiPay не вызван.
3. Сумма с тиынами → 400 `qr_whole_tenge`, оплат нет.
4. Сбой провайдера → 400, оплата `rejected`.
5. `GET …/payments/{pid}/` → оплата с провайдером; чужой заказ → 404;
   без прав → 403.
Существующий `test_cashier_qr_never_calls_the_payment_provider` зелёный.

Фронтенд:
- `debt-orders.test.ts`, `numpad.test.tsx`, `use-pos-flow` редьюсер.
- `pos-screen.test.tsx` (страница `/accounting?view=pos`, телефон):
  поиск → клиент → заказ → сумма (клавиатура, «Весь остаток») → QR
  показан → опрос вернул `confirmed` → «Оплачено»; удалённый счёт; таб
  «История»; недоступный заказ (USD) серый; ошибка создания остаётся на
  шаге суммы.
- Кнопка POS видна при `payments.create` и скрыта без него;
  `resolveView("pos")` на десктопе → `overview`.

Финал: `pytest` целиком, `npm run check`, `npm run build`, затем один
коммит, пуш в ветку и `main`, слежение за CI → деплоем.
