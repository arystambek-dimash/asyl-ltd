# Касса: «Внести оплату» по клиенту — долг гасится от старого заказа к новому

Статус: дизайн утверждён владельцем 01.10.2026 (ответы в чате). Разведка — workflow `wf_258bca6f-3a5`.

## 0. Проблема и решения владельца

Сейчас касса принимает деньги только по одному заказу («Принять оплату» внутри заказа). Владелец хочет так:
клиент приносит сумму, кассир в карточке «Долг · клиент» жмёт **«Внести оплату»**, вводит сумму, и система
сама гасит долговые заказы от старого к новому. Последний заказ при этом может закрыться частично.

| # | Решение |
|---|---------|
| D1 | «Старый» = по дате отгрузки (`shipment.shipped_at`, без неё — `created_at`), затем `id`. «Заказы в долге» в карточке идут в том же порядке, от старого к новому. |
| D2 | Больше всего долга не принимаем: «Максимум к оплате N ₸» и кнопка «Весь долг». Аванса или баланса у клиента нет. |
| D3 | Одно внесение = несколько обычных оплат, по одной на заказ, у всех общая пометка. Плюс одна сводная запись в журнале событий. Новой модели нет. |
| D4 | Способы: наличные, Kaspi-терминал, «удалённая» (`Payment.SETTLED_ON_RECORD`). Для USD только наличные. Kaspi QR и счёт на телефон — по-прежнему по одному заказу. |
| D5 | Заказ магазина, у которого сегодня не день оплаты по графику, пропускается с пометкой «не день оплаты по графику магазина». Деньги идут на следующие заказы. |
| D6 | `settlement_intent` не меняем: частично погашенный заказ из «Ждут оплаты» там и остаётся. |
| D7 | Распределение по всем долговым заказам клиента, всех отделов, как в карточке «Долг · клиент». |
| D8 | Право то же, что у «Принять оплату»: `payments.create`. Распределение строго автоматическое. Чтобы оплатить конкретный заказ, есть кнопка внутри заказа. |

Инварианты: деньги идут только через существующую оплату заказа (`record_staff_payment`), поэтому проверки,
мгновенное подтверждение, статус оплаты, журнал, выписки и отчёты остаются теми же. Валюты не смешиваются:
одно внесение — одна валюта. Корзина = удалённое.

## 1. Бэкенд

### 1.1 Порядок «от старого к новому» — одно место

`apps/orders/debt.py`: `oldest_debt_first(order) -> tuple` — ключ сортировки `(shipped_at or created_at, id)`.
`shipped_at` берётся из `order.shipment`, если она есть. Ключ используют:
- `ClientViewSet.debt_detail`, вместо `orders.sort(key=created_at, reverse=True)`; в выборку клиента добавить
  предзагрузку `shipment`, если её нет, без лишних запросов;
- планировщик внесения (§1.3).

### 1.2 Блокировки клиента — вынести, не копировать

`_lock_scoped_client`, `_lock_client_orders`, `_lock_client_with_orders` и исключение `ClientNoLongerAvailable`
переезжают из `clients/views.py` в сервисный модуль (`apps/clients/services.py` или рядом, без циклов импорта).
Имена становятся без подчёркивания. Вызовы во view переписываются, вторых копий нет.

### 1.3 Новый модуль `apps/orders/debt_payments.py`

- `plan_debt_payment(orders, amount: Decimal | None, *, today) -> DebtPaymentPlan`. Чистая функция, без записи.
  - `orders` — долговые заказы клиента одной валюты, уже отсортированные `oldest_debt_first`.
  - Для каждого заказа: закрыто окно оплаты магазина (`is_payment_window_open(order.store, today)` у отгруженного
    заказа с магазином) → `skipped` с причиной `payment_window_closed`. Иначе `cap = available_to_pay(order)`;
    при `cap <= 0` → `skipped` с причиной `payment_in_progress` («оплата уже в процессе»).
  - Иначе `slice = min(left, cap)`, нулевые доли пропускаются.
  - `total_available` = Σ cap по непропущенным заказам.
  - `amount is None` → план на `total_available` (кнопка «Весь долг»).
  - Результат: `{amount, total_available, slices: [{order, amount, remaining_before, remaining_after, closes}],
    skipped: [{order, reason, detail}]}`.
- `record_client_debt_payment(client, amount, user, *, method, currency, preview=False, note="") -> dict`,
  `@transaction.atomic`:
  1. Проверки до записи: `_positive_money(amount)` (те же коды, что у `add_payment`); `method` из
     `Payment.SETTLED_ON_RECORD`, иначе 400 `debt_payment_method`; `is_payment_method_allowed(currency, method)`
     (код `payment_kzt_only`).
  2. Без `preview`: блокировка заказов клиента по pk, затем клиента (`lock_client_orders` →
     `lock_scoped_client(client.pk, user)`). Порядок тот же, что у удаления клиента и у сервисов заказа.
     Затем перечитать кандидатов: живые `Order.objects` клиента, `is_debt`, `currency=currency`, с
     `select_related("store", "shipment")` и `prefetch_related("payments", "items")`. Сортировка `oldest_debt_first`.
     В `preview` то же самое, но без блокировок и записи.
  3. Нет долга в валюте → 400 `no_debt` («У клиента нет долга в {валюта}»). `amount > total_available` → 400
     `amount_exceeds_debt` с `detail` «Максимум к оплате N ₸» и `max_amount`.
  4. `preview` → вернуть план.
  5. Иначе для каждой доли `record_staff_payment(order, slice, user, method=method, note=common_note)`.
     `common_note` = «Внесение оплаты: 3 150 000 ₸, наличные (3 заказа)»; деньги форматируются существующим
     хелпером. Любая `ValidationError` откатывает всё внесение.
  6. Одна запись `log_event("debt_payment", "Внесение оплаты …", user=user, payload={client_id, department
     (клиента), currency, method, amount, slices: [{order_id, payment_id, amount}]})` без `order`.
     Тип НЕ `payment`: журнал кассы и сводки по дням читают события `payment`. Подпись типа во фронте
     (`lib/event-types.ts`) — «Внесение оплаты».
  7. Вернуть план с `payment_id` в каждой доле.

### 1.4 API

`POST /api/clients/{id}/debt-payment/` на `ClientViewSet`, право `payments.create`; область — `get_object()`
(отдел клиента, как у `debt-detail`).

Тело: `{"amount": "3150000.00" | null, "method": "cash"|"kaspi"|"remote", "currency": "KZT"|"USD", "preview": true|false}`.

Ответ 200:

```json
{"currency": "KZT", "method": "cash", "amount": "3150000.00", "total_available": "75549950.00",
 "slices": [{"order_id": 840, "shipped_at": "2026-09-08T12:00:00+05:00", "remaining_before": "1900000.00",
             "amount": "1900000.00", "remaining_after": "0.00", "closes": true, "payment_id": null}],
 "skipped": [{"order_id": 901, "reason": "payment_window_closed", "detail": "не день оплаты по графику магазина"}]}
```

Ошибки: коды `_positive_money`, `debt_payment_method`, `payment_kzt_only`, `no_debt`, `amount_exceeds_debt`,
а также коды из `record_staff_payment`, если что-то поменялось между предпросмотром и записью.

## 2. Фронтенд

- Карточка «Долг · клиент» (`frontend/src/app/accounting/debts/clients/[id]/page.tsx`): в шапке кнопка
  «Внести оплату», только при `can(me, "payments.create")`. На телефоне кнопка не должна теряться.
- Окно `ClientDebtPaymentModal` (рядом с компонентами оплат). Переиспользуются `Modal` (sheet на телефоне),
  выбор способа, как в «Принять оплату» (отфильтрованный по валюте: USD → только наличные), поле суммы, как в
  «Принять оплату», и `FormError` внутри окна.
  - Переключатель валюты — только когда у клиента долг больше чем в одной валюте (`debt_by_currency`).
  - Кнопка «Весь долг» = `total_available` из предпросмотра.
  - Разбивка из предпросмотра обновляется при вводе (debounce):
    - «#840 · отгружен 08.09 — 1 900 000 ₸ → закрыт»;
    - «#843 — 300 000 из 1 209 500 ₸ → останется 909 500 ₸»;
    - пропущенные заказы с причиной.
  - Превышение показывает «Максимум к оплате N ₸» и выключает «Подтвердить».
  - «Подтвердить · N ₸» → POST без `preview` → уведомление «Внесено N на K заказов», затем `refresh()` страницы.
- Фронт ничего не пересчитывает: суммы и разбивку отдаёт сервер.
- Тип ответа — в `lib/types.ts` или `lib/debt-orders.ts`, без дублей хелперов.

## 3. Тесты

Бэкенд (`DB_NAME=asyl_<метка>`):
- распределение на 3 заказа с частично закрытым последним;
- порядок по отгрузке: заказ задним числом и вагон по отчёту;
- резерв (заказ с запрошенной или полученной оплатой) уменьшает долю, при нуле заказ пропускается;
- закрытое окно магазина — пропуск;
- USD + kaspi → `payment_kzt_only`;
- у клиента KZT и USD: трогается только выбранная валюта;
- заказ в корзине не оплачивается;
- сумма больше долга → `amount_exceeds_debt` с `max_amount`;
- `preview` ничего не пишет;
- одна неудачная доля откатывает всё;
- чужой отдел → 404 или 403;
- без `payments.create` → 403;
- событие `debt_payment` и общая пометка на оплатах;
- `debt_detail` отдаёт заказы от старого к новому.

Фронт: окно (предпросмотр, «Весь долг», превышение, выбор валюты и способа, ошибка внутри окна, отправка),
страница (кнопка видна только с правом, после оплаты — уведомление и `refresh`), подпись события.
